## Hosting rewrite for Vercel + Neon + Cloudflare R2 (branch `vercel`)
Goal: run the platform without a server of our own. The code supports both: the Docker deployment is unchanged and still works. Guide: `docs/VERCEL.md`.
- **Phase 1, storage**: local disk or S3-compatible object storage behind one facade (same function names for the ~15 callers); presigned downloads.
- **Phase 2, direct uploads**: guest photos (up to 100 MB), the mosaic master (25 MB) and offline-sync files go straight to the bucket with one-file signed addresses (size and type signed), then the API re-checks them exactly like the plain route; the event package is served from storage.
- **Phase 3**: live streams removed (screens poll every 4 s); strict rate limits counted in Postgres (shared across instances); scheduled jobs as cron routes behind `CRON_SECRET`.
- **Phase 4**: the API runs as one function inside the Next.js project (same origin, so cookie/CSRF/CSP are unchanged); big downloads redirect to signed addresses (a function cannot return more than ~4.5 MB; real pictures reach 4-11 MB); ZIP export written to storage as a multipart stream; Vercel startup checks; `vercel.json` (cron schedules, build with migrations).
- **Verified** (automated): 475 API tests pass on the disk backend and on the S3 backend (in-memory stand-in), plus 63 shared tests; typecheck and build clean. Against a **real S3-compatible server (MinIO)**: the storage contract, multipart upload of 20 MB, prefix deletion of 1,100 objects, and that a signed upload address refuses a larger body, another type, another key and an expired address. A production build of the site with the API inside it, on real Postgres and MinIO, driven over HTTP and in a **real browser under the production CSP**: sign-in, direct upload, frame, adjust, server preview, download and the share-button fetch, ZIP export, event package, mosaic, QR redirect, cron, database rate limit. Function size when traced about 64 MB (limit 250 MB). Picture engine peak memory 210-430 MB and 0.6-1.9 s per job on a development PC.
- **Found by running it for real and fixed**: batch delete refused by a real S3 server (now falls back to one-by-one); the ZIP stream class not accepted by the multipart uploader; `/q/<code>` not reaching the API from a route handler; the Docker web build would have packaged the whole API (now a build-time switch); a build-output folder briefly committed (removed).
- **NOT verified**: anything on the real Vercel, Neon and **Cloudflare R2** (R2's own CORS and its handling of signed headers; MinIO is not R2), a real phone upload over mobile data, the share sheet on Android/iPhone, the .NET print agent following the redirect to the bucket, function cold-start time and compose time on Vercel's CPUs, Neon behaviour under a burst, Vercel Cron actually firing. `docs/VERCEL.md` section 7 is the checklist for the real deployment.
- **Known limits of this setup**: no live push (polling load: about 900 requests an hour per open screen); the global rate limit is per function instance (add a Vercel Firewall rule); a single request must finish in 300 s; ZIP exports are cut at 5,000 pictures.

## Overall status
All 17 phases of the plan are built and tested in software, and the platform can be hosted either with Docker on a server or on Vercel + Neon + R2 (branch `vercel`). The platform is NOT proven for a live event until the hardware and device checklist in `docs/ACCEPTANCE.md` has been done on the real equipment.
